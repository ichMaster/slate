## 1. The verdict: does `lv_xml` run on the ESP32-P4?

### **GO.**

```
SLATE_LEDGER xml_bytes=1872
SLATE_LEDGER lv_xml=GO lvgl=9.4.0
SLATE_LEDGER xml_register_us=1267 xml_create_us=3516
SLATE_LEDGER lv_pool_total=62780 lv_register_cost=1288 lv_widget_tree_cost=1912
```

| | |
|---|---|
| Page size | 1872 bytes of XML |
| Parse + register | **946–1267 µs** (across runs) |
| Instantiate widget tree | **3366–3516 µs** |
| Register cost | **1288 bytes** of LVGL's pool |
| Widget-tree cost | **1912 bytes** of LVGL's pool |
| LVGL pool | 62 780 bytes total, ~48 400 free after the page |

`lv_xml` compiles for the P4 with its vendored expat, registers a page, and
instantiates a live widget tree. **The fallback — a vendored ~6 KB SAX parser
with the vocabulary hand-mapped to `lv_*` — is not needed and should not be
built.**

### Consequence for v1.3, and it is not the obvious one

The module works, but **LVGL removed it in 9.5.0**. Verified against upstream
trees rather than inferred — a recursive search of the `v9.5.0` tree finds no
`lv_xml` source anywhere, only ThorVG's unrelated `tvgXmlParser`:

| LVGL tag | `src/others/xml/` |
|---|---|
| v9.2.0 | absent (module did not exist yet) |
| v9.3.0 | **present** |
| v9.4.0 | **present** ← pinned |
| v9.5.0 | **removed** |

The Tab5 BSP pulls `esp_lvgl_port ^2`, which resolves LVGL to **9.5.0** by
default, so the untouched dependency graph produces a platform with **no XML
renderer at all** — and it fails as a missing header, not as a decision.
`m0/firmware/main/idf_component.yml` pins `lvgl/lvgl ~9.4.0`.

**So the risk v0.1 was built to retire is not "can the P4 parse XML" (it can) but
"will the XML module still exist".** v1.1 should record the LVGL pin in
ARCHITECTURE §Stack as a project-level constraint, and v1.3 should decide
deliberately whether the component machinery is built on a module upstream has
already dropped, or on the SAX fallback after all. That decision is now
informed, which is what this milestone was for.

**Two smaller findings.** `LV_USE_XML` hard-requires `LV_USE_OBJ_NAME`, which
Slate wants anyway: `lv_obj_find_by_name()` is exactly the lookup that turns a
`data` update's `id` into a widget, and the applicator uses it. And the real API
is `lv_xml_register_component_from_data` / `_from_file`, not
`lv_xml_component_register_from_file` as the roadmap has it.

## 2. Panel revision

```
SLATE_LEDGER i2c_devices=9 addrs=0x10 0x28 0x32 0x40 0x41 0x43 0x44 0x55 0x68
SLATE_LEDGER panel_revision=ST7121 touch=ST712x st712x_fw=1
Discovered board version 3 (LCD ST7121, Touch ST712x, FW 1)   <- the BSP agrees
```

**Board version 3: LCD ST7121, touch ST712x firmware 1.** A third answer to the
roadmap's "ILI9881C vs ST7123/ST7121". ST7123 and ST7121 share I2C address
`0x55` and are separated only by the touch firmware version byte (3 vs 1), so
the probe reads it rather than guessing.

### A BSP defect that will be met again

`bsp_display_start()` calls a private `bsp_get_board_version()` which enables
**only** `BSP_FEATURE_TOUCH` before probing I2C for a touch controller. On this
board the touch controller does not appear on the bus until the **LCD rail** is
also powered, so the probe finds nothing and the BSP `assert`s —
`E M5Stack Tab5: Unsupported board version!` — which presents as a boot loop,
not a diagnosable error. The difference is stark:

```
touch rail only : i2c_devices=7  0x10 0x32 0x40 0x41 0x43 0x44 0x68
LCD + touch     : i2c_devices=9  0x10 0x28 0x32 0x40 0x41 0x43 0x44 0x55 0x68
                                      ^^^^                        ^^^^
```

`slate_panel_probe()` enables both rails before the BSP runs. This is a defect in
`espressif/m5stack_tab5 1.3.0` against board version 3, not something Slate
chose, and **v1.1 will meet it again** the moment it stands up the kept
`firmware/` tree.

## 3. Silicon revision — a build-splitting constraint

**ESP32-P4 revision v1.3**, MAC `e8:f6:0a:e2:df:cc`, USB-Serial/JTAG.

ESP-IDF 5.5 defaults to requiring chip revision **v3.1+**, so the bootloader
refuses to flash this board outright:

```
bootloader.bin requires chip revision in range [v3.1 - v3.99]
(this chip is revision v1.3)
```

ESP-IDF treats P4 `<3.0` and `>=3.0` as **mutually exclusive** targets — "huge
hardware difference", in its own Kconfig — so this is
`CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y` + `CONFIG_ESP32P4_REV_MIN_100=y`, **not**
`--force`.

**A binary built this way runs on 0.x/1.x boards and not on 3.x ones.** If a
second Tab5 with 3.x silicon appears, it needs its own build, not a tweak to
this one. That is a fleet constraint, and it is the reason the roadmap asked for
the revision to be recorded.

## 4. Memory and versions

```
SLATE_LEDGER lvgl_version=9.4.0
SLATE_LEDGER idf_version=v5.5.5
SLATE_LEDGER free_heap_internal=284679 free_heap_psram=29959716
```

| | |
|---|---|
| ESP-IDF | v5.5.5 |
| LVGL | 9.4.0 (pinned — see §1) |
| Tab5 BSP | `espressif/m5stack_tab5` 1.3.0 |
| Free internal heap after boot | **284 679 bytes** |
| Free PSRAM after boot | **29 959 716 bytes** |
| LVGL pool | 62 780 bytes (`LV_MEM_SIZE_KILOBYTES=64`) |

These are v0.1's choices, **not** the project's pins: ARCHITECTURE §Stack defers
real pinning to v1.1.

**Two memory findings worth carrying forward.**

*The draw buffers must live in PSRAM.* `bsp_display_start()`'s defaults put them
in internal DMA memory and software rotation needs a further full-screen buffer;
once `esp_hosted` is linked in for WiFi there is not enough internal RAM and the
display fails to start at all ("Not enough memory for LVGL buffer (rotation
buffer) allocation!"). Starting with `buff_spiram = true` fixes it and raises
free internal heap from 128 KB to 284 KB.

*The stock fonts are large.* Montserrat 24 and 48 alone took the binary to within
**3%** of the stock 1.5 MB app partition. `partitions.csv` gives the app 4 MB of
the 16 MB flash instead. v1.3 compiles two real faces at five size roles, which
will cost considerably more — the partition layout should be settled then, not
discovered.

## 6. Open blocker — WiFi needs co-processor firmware

The ESP32-P4 has **no radio**. The Tab5 pairs it with an **ESP32-C6-MINI-1U**
reached over `esp_hosted`'s SDIO link, and the SDIO link never comes up:

```
E sdmmc_common: sdmmc_init_ocr: send_op_cond (1) returned 0x107   (ESP_ERR_TIMEOUT)
E eh_host_port_sdio: sdmmc_card_init failed                        (repeats forever)
```

Ruled out along the way:

- **Not power.** `BSP_FEATURE_WIFI` (IO expander pin `BSP_WIFI_EN`) is asserted
  at the top of `app_main`, before esp_hosted starts probing ~2 s into boot. The
  log confirms `C6 powered` at 1841 ms against the first probe at 2881 ms.
- **Not pin configuration.** esp_hosted's defaults already match the board —
  reset GPIO 54, SDIO slot 1, 4-bit, 40 MHz.
- **A pure timeout**, meaning the C6 does not answer at all rather than answering
  wrongly.

**The remaining explanation is that the C6 is not running `esp_hosted`
co-processor firmware.** esp_hosted ships that firmware as an ESP-IDF project
(`examples/<feature>/cp/`) flashed with `eh.py -p <port> flash` — **over serial**,
and the Tab5 exposes only the P4's USB port. Flashing the C6 is therefore a
vendor-procedure question (M5Burner, or an M5Stack-documented bridge), not
something the build can resolve.

**Everything that does not cross the network is proven.** The blocker gates the
DoD demonstration and §5's figures, nothing else.

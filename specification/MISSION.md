# Mission — Slate

## In one sentence

Slate is a thin-client application platform — a mainframe terminal model rendered with LVGL — where a dumb-but-pretty ESP32 device renders pages a server sends, an application is one declarative XML page plus one server-side handler, and new applications are generated by Claude Code from a Markdown description and are live immediately, without ever touching the firmware.

## What we are building

A hardware terminal for personal servers. The device (M5Stack Tab5 first: ESP32-P4, a 5-inch 1280×720 touch screen, an attachable 70-key keyboard) holds no logic, no data, and no truth except the user's in-progress input; the server holds everything else. Between them travels a narrow protocol: the server sends *content*, the device sends *events*. The unit of software is a **page** — an XML file in LVGL's declarative format, assembled only from a small, closed component vocabulary. A page plus its server-side handler is an **application**.

Three consequences follow, and they are the point of the whole design: the firmware stabilises early (new applications appear by adding files on the server — no reflashing, no compile cycle); applications are generatable (a page is constrained declarative text that Claude Code writes from a Markdown description and proves with a headless validator, no hardware required); and the platform is portable (any LVGL device can host the same shell — Tab5 first, Cardputer and others later, differing only in layout).

The flagship application is the **Claude Code companion**: a live dashboard of a running session, a full-screen question page answered from the keyboard, and a two-way chat with the session itself. Around it grow a status console, a server terminal, Markdown and Wikipedia browsers, notes — and, as optional ports, the author's existing projects: Srotas, a Telegram chat, RoboFace, and Lumi, the last two with voice.

## For whom

A private project for the author — one person, a handful of personal servers (a Mac, a Pi), a trusted LAN or Tailscale. Multiple servers are independent worlds, open simultaneously. This is not a product and not a public service; the implementing audience is Claude Code, and the generating audience is Claude Code too — the platform exists so that describing an application in Markdown is enough to have it running on the desk.

## Principles

- **Device owns feel, server owns meaning.** Touch feedback, scrolling, text entry, and switching are instant and local; every decision and every value is the server's. The device never has its own truth except the user's in-progress input.
- **Structure is static, content is dynamic.** A page's XML is fetched once and cached; everything that changes is a targeted update naming an `id`. A page is never re-sent to change a number — replacement is an explicit navigation.
- **A small, closed vocabulary.** Pages are assembled only from the component library, never raw LVGL widgets; the dynamic-property set is closed at eight. Predictable generation matters more than expressive range.
- **Growth on demand, in spec and in build order alike.** A component, a font, a property enters the platform only when a named application cannot live without it — and is built only when that application's step arrives.
- **Roles and tokens, never pixels and hex.** Type, colour, and spacing are named roles the firmware maps per device — the mechanism behind dark mode, cross-application consistency, and future screens.
- **Pages are data, never instructions.** The action registry is the security boundary: a page may reference declared actions, never invent them. A generated page cannot do anything the firmware was not already built to do.
- **Events never fail silently.** The outbound queue is bounded; past the limit the oldest are dropped *and the user is told*.
- **Every proof first, then only additions.** v0 concentrates the walking skeleton, every proof-of-concept, and the test scaffolding; each phase after it adds functionality the platform did not have — no phase formalises or re-records what an earlier one proved. Applications are their own phases, interleaved at the earliest point the platform can carry them; nothing is built ad-hoc to be migrated later.
- **One repository.** The component definitions and the action registry are a contract with three consumers — firmware, server, validator — and in one repo they cannot drift.
- **Trusted network as a decision.** v1 carries no protocol auth; secrets live server-side; untrusted page servers are a non-goal.
- **English specs, Ukrainian first-class on screen.** Specification documents are English; both compiled font faces carry Cyrillic from the component system onward.

## Non-goals

- Not a web browser: no HTML, no JavaScript, no DOM. Not a code-download system. Not a UI builder.
- No PTY (the terminal is command → output by design); no inline links or images inside flowing text (block-level only); no third font face; no wake word, no barge-in, no codec beyond PCM16 until real bandwidth demands one.
- No untrusted page servers, no open public access, and no direct internet from the device — the server is always the proxy.
- No mass-market ambitions; multi-user, accounts, and deployment machinery are out of scope in every planned version.

## Glossary

- **Page** — an XML file in LVGL's declarative format describing one screen's structure; fetched by base path, cached on SD, revalidated with `If-None-Match`.
- **Application** — a page (or several) plus its server-side handler; a directory in `apps/`.
- **Component** — a `<component>` definition from the platform library (`components/`), the only building blocks pages may use; each declares static props and its `id`-addressable dynamic properties.
- **Dynamic property** — one of the closed set of eight (`text`, `value`, `visible`, `enabled`, `color`, `progress`, `items`, `image`) the protocol may update in place.
- **Shell** — the only screens compiled into firmware: server picker, application switcher, status bar, error banner, navigation chrome.
- **Session** — the binding of an open application's two halves — a live LVGL screen on the device, a handler state on the server — under a device-minted `session_id`; created lazily by the server on first sight.
- **Index page** — an ordinary page at the server root that, by convention, lists the server's applications; the shell's landing point.
- **Parameterised page** — one cached page structure addressed with a query string (`?t=Lviv`); the query selects content, never structure, and the full path lives in history.
- **Token / role** — a named value (`accent`, `body`, `md`) the firmware resolves per device and theme; pages never carry pixels or hex (raw hex is an escape hatch for data-driven colour only).
- **Action registry** — the declared file of action names (each local or server-bound) that firmware loads and pages may reference; the security boundary.
- **Manifest** — the machine-readable ground truth of components, props, dynamic properties, and actions; read by the validator and the authoring agent.
- **`notice`** — the one message a backgrounded session may send: a status-bar badge, never content; tapping it switches to the application.
- **Walking skeleton** — v0.1's throwaway end-to-end prototype: the counter, the clock, `doc-view` v0, the trimmed wire, and the PoC ledger.
- **PoC ledger** — the record written at v0.1's exit: the `lv_xml` go/no-go verdict, parse/heap/render measurements, and the panel revision.
- **Validator** — the host-compiled CLI (`slate-validate`) that proves a page against the manifest and registry and renders it to PNG; what closes the agent's feedback loop.
- **Tail re-send** — the streaming pattern of `log-view` and `chat-view`: the server re-sends the growing tail with set semantics; there is no append operation.
- **Fake device** — the host-side script (from v0.1, under `tools/`) that speaks the device's wire so every server behaviour is testable without hardware.
- **Second wave** — the optional ports built after the platform is complete: Srotas, Telegram, RoboFace, Lumi.
- **World** — one server as the user experiences it: its index, its applications, its sessions; several worlds are open at once, one WebSocket each.
